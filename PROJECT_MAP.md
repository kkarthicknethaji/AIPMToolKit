# Project Map — Product Studio

**Purpose:** This file exists so that a request touching one feature area only requires reading the 1–3 files this map points to — not the whole codebase. Treat every entry as a targeting aid: precise enough to avoid opening unrelated files, and no more verbose than that job requires. Narrative history (why a fix was made across several past versions) belongs in `CHANGELOG.md`; keep entries here to current-state facts and only the "why" detail that changes where to look or what to avoid touching.

## File responsibilities

### Entry point
`index.html` — app shell, tab buttons (mm, cc, pi, mi, la, sc), Story Canvas HTML structure, script/CSS references. Tab button IDs: `tab-mm`, `tab-cc`, `tab-pi`, `tab-mi`, `tab-la`, `tab-sc`. Content area IDs: `out-body` (mm), `cc-tab`, `pi-tab`, `mi-tab`, `la-tab`, `sc-tab`.

### Auth entry point
`login.html` — standalone login/signup page. No app shell. Loaded by unauthenticated users. Redirects to `index.html` on success.

### Auth module
`scripts/auth.js` — Supabase client init and all auth functions. Loaded by both `login.html` and `index.html`.
- `authInit()` — initialises Supabase client singleton (SUPABASE_URL + SUPABASE_ANON_KEY)
- `authSignIn(email, password)` — supabase.auth.signInWithPassword(); maps errors to readable strings
- `authSignUp(email, displayName, password)` — validates AUTH_DOMAIN, supabase.auth.signUp() with display_name in user_metadata
- `authSignOut()` — supabase.auth.signOut(), redirects to login.html
- `authGetSession()` — returns active session or null; used by auth gate in main.js
- `authGetUser()` — returns { id, email, displayName } for signed-in user
- `authResetPassword(email)` — supabase.auth.resetPasswordForEmail()

`styles/18-auth.css` — login page layout and form styles. Loaded by `login.html` only.

### Netlify configuration
`netlify.toml` — build config: publish dir, functions dir, `/api/anthropic` redirect rule
`netlify/functions/anthropic-proxy.js` — serverless proxy: receives browser requests, forwards to Anthropic server-side with user key in Authorization header. Fixes CORS for org-managed API keys. BYOK: no env variables needed.

### Render.com proxy backend
`proxy/server.js` — Express proxy backend deployed on Render.com. POST /api/anthropic endpoint. CORS locked to productdiagnostics.netlify.app. Rate limit 20 req/min per IP. Deployed separately from the Netlify frontend — do NOT modify without testing on Render. Auth: `requireAuthStrict` (JWT-required, no local-dev bypass) + `requireCompanyAdmin`, mounted on `/api/team/*` — seven admin-only routes (list/invite/set-role/disable/enable/delete/resend/revoke), all service-role-keyed via `supabaseAdmin`, scoped by both `company_id` and target `user_id` on every query. Role-change/disable/delete admin-count safety is enforced via three Postgres RPCs (`team_set_role_safe`, `team_disable_safe`, `team_delete_member_safe` — see `phase4-rpcs.sql`), not in-process logic — closes a concurrency gap a plain application-level count-then-update can't close. `/api/anthropic` uses `requireAuthStrict` plus `requireActiveCompanyMember` (calls the shared `is_active_company_member()` RPC, see `v8113-migrations.sql`) — this is the highest-frequency endpoint in the app. JWT verification includes explicit `issuer`/`audience` checks.

- **v9.32 AI Cost Control Tower: OpenAPI Ingestion Layer** — a consumer-tier `/v1` REST API letting other internal HCLTech apps (not just Product Studio) write their own usage/outcome events into the shared Cost Control Tower tables. Mounted near the bottom of the file, ahead of the pre-existing 200-always 404 catch-all: `v1IngestionLimiter` (rate limit, same `RATE_LIMIT_MAX`/`RATE_LIMIT_WINDOW_MIN` shared config), then `apiKeyAuth(supabaseAdmin)` (`proxy/middleware/apiKeyAuth.js`) once ahead of all four `proxy/routes/v1/*.js` routers (mounting it per-router would re-run it up to 4x per request, since Express falls through an unmatched router to the next `app.use()` at the same path), then `express.json()` plus a dedicated JSON-parse-error handler, then the four routers, then a `/v1`-scoped 404 handler (this API uses real HTTP status codes throughout — 400/401/404/429/500 — a deliberate exception to this file's own always-200-error-in-body convention, which stays untouched for every route above it). `/docs` (a separate, unauthenticated static route, `express.static` over `proxy/openapi/`, with a `/docs` → `/docs/` redirect so `docs.html`'s relative `spec-url` resolves) serves the published Redoc reference. Full endpoint/security/schema detail lives in `ai-cost-tower-openapi-ingestion-spec.md` and the "Common request routing" table below — this bullet is the file-level orientation only.

- **AI Trace Layer** (spec `ai-trace-layer-spec-v0.11-final.md`) — correlates the N flat, unconnected `mt_ai_usage_events` rows one Requirement Agent conversation produces into one `mt_ai_traces` row + ordered `mt_ai_spans` rows, and extends the same write path to a second, product-agnostic span shape (`tool_call`, for a step with no LLM API call at all — no Product Studio caller exercises this yet). `_insertAiUsageEvent()` no longer does a direct `.from('mt_ai_usage_events').insert()` — it calls the shared `mt_ai_record_usage_event_with_span()` RPC (also called by `usageEvents.js`), so there is exactly one place a usage event and its optional span/trace are ever written, for both Product Studio's own calls and the external `/v1/usage-events` path. An RPC exception on a genuine idempotency conflict (`ERRCODE 23514`) is caught and logged here, never surfaced to the end user — `_insertAiUsageEvent()`'s own long-standing "telemetry is best-effort" principle, unchanged; the external route maps the same exception to `409` instead, since that caller is an API consumer, not a user waiting on a chat response. Two new routers mounted alongside the existing four: `tracesRouter`/`toolSpansRouter` (`proxy/routes/v1/traces.js`/`toolSpans.js`). Schema in `sql/ai-cost-tower-trace-layer-migration.sql` (NOT run by Claude Code) — `mt_ai_traces`, `mt_ai_spans` (dual shape, enforced by a `CHECK` constraint rather than by a second, independently-derived comparison), `mt_ai_usage_events.trace_id`, and the two RPCs (`mt_ai_record_usage_event_with_span`, `mt_ai_record_tool_span`).

- **v9.33.01 AI Trace Layer: Payload Capture Infrastructure** (spec `ai-trace-layer-payload-infra-followup-spec-v0.7.md`, D.7 items 1-3 — item 4, the purge mechanism, is a separate future spec) — closes the gate a real credential needs before `mt_ai_trace_payloads`/`POST /v1/trace-payloads` (built v9.33.02, see below) can ever be turned on. Four new `mt_company_apps` boolean columns (`sql/ai-cost-tower-trace-layer-payload-infra-migration.sql`, NOT run by Claude Code): `scope_usage_write`/`scope_traces_write` (reserved, non-enforced this release, default `true` — no route reads them yet) and `scope_payloads_write`/`payload_capture_enabled` (default `false`). `apiKeyAuth.js` attaches both as `req.scopes`/`req.payloadCaptureEnabled`; `requirePayloadCaptureWrite.js` is the composed check for the route (both must independently pass), mounted at the route level in `tracePayloads.js` as of v9.33.02. Also closes a live bypass the spec's own diligence pass found: `/v1/usage-events`'s `provider_usage_raw` (arbitrary JSONB, no prior validation) could carry full prompt/response text under any key name and persist exactly as submitted — `usageEvents.js`'s `_validateItem()` now allowlists its exact keys/types per declared `provider` (`anthropic`/`openai`/`gemini`, each traced to that provider's adapter in `providerAdapters.js`; unrecognized/omitted provider falls back to Anthropic's table), rejecting — not stripping — any item with an unlisted key, wrong type, oversized string, excess nesting, or a total size over 2048 bytes. `/v1/traces` and `/v1/tool-spans` needed no change — both already write only fixed named fields, confirmed by direct code read, not by the earlier drafts' assumption.

- **v9.33.02 AI Trace Layer: Payload Capture** (`mt_ai_trace_payloads`, `POST`/`GET /v1/trace-payloads`) — the missed item from v9.33.01's own scope, not a new feature; the original spec's Part B.3 schema text was never committed to this repo, so this is a fresh design grounded in this repo's own conventions (`mt_ai_traces`/`mt_ai_spans`/`traces.js`), reviewed and approved directly rather than re-derived from spec text. `mt_ai_trace_payloads` (`sql/ai-cost-tower-trace-layer-trace-payloads-migration.sql`, NOT run by Claude Code — confirmed applied to both pgt-dev and pgt-prod): one row per usage event (`UNIQUE` FK on `usage_event_id`), `company_id`/`app_id` stored directly (not just reachable via join, so a future dashboard/debugging query can filter by tenant without one), `request_payload`/`response_payload` as opaque `JSONB` with a `CHECK` constraint requiring at least one non-null (code-review fix — the route already enforced this in JS, but nothing backed it at the schema level for any other writer), `expires_at` defaulted to a 90-day retention window — the purge mechanism itself (D.7 item 4) remains out of scope, nothing acts on this column yet. `proxy/routes/v1/tracePayloads.js`: `POST` validates `usage_event_id` as a UUID and both payload fields as plain objects (400, not a 500 or a silent accept, on either — same "reject over strip" philosophy as `provider_usage_raw`), ownership-checks `usage_event_id` against the caller's own `(company_id, app_id)` before insert, and is idempotent via `insertIdempotentStrict()` with a custom `compareFn` (`_deepEqual()` — key-order-independent; Postgres `jsonb` doesn't preserve key order on read-back, so even a naive `JSON.stringify` compare would spuriously 409 a legitimate identical retry, a code-review catch) and `extraMatch` (`company_id`/`app_id`, since this table's conflict target — `usage_event_id` alone — isn't already tenant-scoped the way `traces.js`'s own `conflictColumns` are). `GET` gets the same UUID validation and reuses the same `requirePayloadCaptureWrite` gate (no separate `payloads:read` scope exists), returning the full row, since this only ever hands a payload back to the exact credential that wrote it. `idempotencyStrict.js` itself was rewritten in the same pass (round 2 of code review) to support this — it no longer delegates to `insertIdempotent()` internally (that cost an extra round trip on every conflict), now doing one upsert + one combined follow-up SELECT, plus a `!existing` null-guard that was a real latent gap in the pre-v9.33.02 version (never triggered in production, but the same bug class just found in `tracePayloads.js`'s own first draft) — this also benefits `traces.js`, its existing consumer, with no change to its call site or behavior (verified with a mocked functional test covering fresh-insert, key-order-independent match, genuine mismatch, and the null-guard path). `proxy/openapi/openapi.yaml` gains the `trace-payloads` tag, both operations, a `PayloadRecord` schema, and a v1.2.0 API-contract-changelog entry — published automatically via the existing `/docs` Redoc page.

- **v9.34 Universal Payload Capture** — extends payload capture (v9.33.01/.02, above) to every Product Studio AI call, not just Requirement Agent's — the ~15 other feature files never send `client_trace_id`, but every one of them (plus `home.js`'s AI Recommendations flow, a confirmed `callAPI()` bypass that independently constructs the same request shape) lands on the same `proxy/server.js` `/api/anthropic` endpoint, which is what makes a backend-only change sufficient; no feature file is touched. `mt_ai_record_usage_event_with_span()` (`sql/ai-cost-tower-trace-layer-payload-rpc-extension-migration.sql`, NOT run by Claude Code — DROP + CREATE, 34-arg signature → 36-arg, since a plain `CREATE OR REPLACE` cannot add parameters without leaving the old signature callable as a separate overload, the same reason `-step4-reconciliation.sql` needed a DROP) gains `p_request_payload`/`p_response_payload` (both `JSONB DEFAULT NULL`) and conditionally writes to `mt_ai_trace_payloads`, gated independently of the trace/span condition on the same `scope_payloads_write`/`payload_capture_enabled` columns the external `/v1/trace-payloads` route already gates on (same predicate, implemented twice — SQL and Node — not one shared function, since nothing in this codebase lets either call into the other). Adds `payload_capture_status` (`'captured'`/`'gate_disabled'`/`'not_requested'`) to the `RETURNS TABLE`, so a denial is observable without changing the usage-event write's own success/failure contract; on a `client_call_id` replay, this reflects whether a payload already exists for the original call (a lookup against `mt_ai_trace_payloads`, not a re-derivation), since nothing is requested or denied on the replay itself. `proxy/lib/costTower/usageEventRpcParams.js` — the single field→`p_*` mapping shared by `server.js` and `usageEvents.js` — gained the two new mappings; without this the RPC signature change alone would have shipped inert, since this helper does an explicit named-field mapping rather than passing fields through. `server.js`: all four `_insertAiUsageEvent()` call sites (non-streaming success/error-payload, streaming success/mid-stream-error, streaming pre-stream buffered error, and the outer network/timeout catch-all) now offer `request_payload` unconditionally — the request is fully constructed before any of these outcomes is known — with `response_payload` following one canonical `{schema, streamed, content_type, error, content}` envelope (`content_type`: `'adapter_normalized'` for the non-streaming path's already-adapter-normalized `_normalized` object, `'accumulated_text'` for the streaming path; `content: null` wherever no response was actually produced). Streamed response text is accumulated inside `_streamUpstreamOnce()` at the parsed-SSE-delta level (`parsedEvt.delta` — already a complete, whole JS string via `StringDecoder` + JSON parse), never off a raw network `chunk` (which this same function's own `StringDecoder` exists specifically because it is *not* guaranteed to end on a character boundary) — accumulation stops at the last delta that fits under `MAX_PAYLOAD_CAPTURE_BYTES` (100KB, retunable) rather than ever slicing a completed buffer/string, so a capped capture can never land mid-character. A genuine mid-stream abort still keeps whatever partial text was accumulated (`truncated: false`, distinct from hitting the byte cap). `_insertAiUsageEvent()` now reads the RPC's returned `payload_capture_status` and logs a `warn`-level, payload-content-free line on `'gate_disabled'`. Also fixes a pre-existing, independent scope bug found while wiring the outer catch-all: `body` was a `const` declared inside the route's `try` block, so the catch block's existing bare `body.model` reference threw `ReferenceError` on every network-failure/timeout call reaching it — hoisted to a `let` before the `try`, alongside `_clientCallId` etc., which were fixed the same way for the same reason in an earlier build. Confirmed applied to both pgt-dev and pgt-prod (one signature, 36 args, verified via `pg_proc`). Live testing against pgt-dev also found a real gap in the migration script itself: submitting the whole file as one script lets Postgres wrap it in a single implicit transaction, so STEP 3's own test-call `ROLLBACK` silently undid STEP 1's DDL along with it — fixed with an explicit `COMMIT` between the two.

`proxy/middleware/apiKeyAuth.js` — v9.32. Resolves a `/v1` request's Bearer token to `(company_id, app_id)` by SHA-256-hashing it and matching `mt_company_apps.credential_hash` — the one auth path in this app that never touches a Supabase Auth session (a machine credential has none), unlike `requireAuthStrict`/`requireActiveCompanyMember` above. Sets `req.companyId`/`req.appId` (same shape `requireActiveCompanyMember` sets, so downstream `/v1` route code reads identically regardless of which auth path resolved it). Also opportunistically throttle-updates `credential_last_used_at` (fire-and-forget, 5-minute window, mirroring `_checkBudgetAlertsOpportunistic()`'s own throttle-map pattern above). **v9.33.01 Payload Capture Infrastructure**: the same credential-lookup query also selects `mt_company_apps`'s four new scope/toggle columns (no second round-trip) and attaches `req.scopes` (`usageWrite`/`tracesWrite`/`payloadsWrite`) and `req.payloadCaptureEnabled`.

`proxy/middleware/requirePayloadCaptureWrite.js` — v9.33.01, AI Trace Layer: Payload Capture Infrastructure. Route-level-only middleware for `POST`/`GET /v1/trace-payloads` — `403`s unless `req.scopes.payloadsWrite` AND `req.payloadCaptureEnabled` both pass, collapsed into one composed check so a future implementer can't wire only one of the two independently-required gates. Not mounted globally (would incorrectly block every other `/v1` route) — v9.33.02: mounted at the route level, on both methods, in `tracePayloads.js`, its first consumer.

`proxy/routes/v1/usageEvents.js` — v9.32. `POST /v1/usage-events` (single object or batch, cap 500, bounded concurrency of 20 in-flight at once — not fully sequential, since items are independent, non-transactional records per the endpoint's own batch semantics), `PATCH /v1/usage-events/{client_call_id}/units-generated`, `GET /v1/usage-events` (keyset-paginated read-back scoped to the caller's own `(company_id, app_id)`, with `calculated_cost` computed application-side against `mt_model_pricing` — deliberately not via the existing `mt_ai_cost_events_list` RPC, whose auth check assumes a human Supabase Auth session). A caller-supplied `outcome_id` is ownership-checked (one batched query per distinct id per request, not one query per item) before insert, and any foreign-key violation (e.g. a stale `outcome_id`) is translated to `400`, not a bare `500`. **AI Trace Layer**: `POST` now accepts optional `client_trace_id`/`agent_name` (the latter required if the former is present, checked here before the RPC ever sees it) and calls `mt_ai_record_usage_event_with_span()` instead of `insertIdempotent()` directly — that RPC's own `23514` conflict exception maps to `409` (not `400`), which is why the single-item response path now looks up its status by `error.type` instead of hardcoding `400` for every error. `GET`'s select list gained `trace_id`. **v9.33.01 Payload Capture Infrastructure**: `_validateItem()` gained `_validateProviderUsageRaw()` — allowlists `provider_usage_raw`'s exact top-level (and, for one key per provider, one level of nested) keys/types, keyed on `item.provider || 'anthropic'` (three tables — Anthropic, OpenAI, Gemini — each traced to that provider's extraction code in `providerAdapters.js`; an unrecognized/omitted provider falls back to Anthropic's, the strictest). Rejects (400/per-item error), never strips, on an unlisted key, wrong type, oversized string, excess nesting, or total serialized size over 2048 bytes. Gemini's `input_tokens_by_modality` is accepted as any array with no element-shape check — the one field in this allowlist without one, an explicit accepted exception (element shape unconfirmed in live code), not a precedent.

`proxy/routes/v1/traces.js` — AI Trace Layer. `POST /v1/traces` (explicit trace creation, idempotent on `client_trace_id` via `insertIdempotentStrict()` — `409` on a genuine `agent_name`/`session_id` conflict, not a silent overwrite; not the only way a trace is created, since `POST /v1/usage-events` and `POST /v1/tool-spans` both create one implicitly too), `PATCH /v1/traces/{id}` (sets `completed_at` only — no `execution_result` field exists in this schema at all), `GET /v1/traces/{id}`, `GET /v1/traces/{id}/spans` (every span in `sequence_order`, embedding its `mt_ai_usage_events` row via a PostgREST foreign-table embed for an `llm_call` span, `null` for a `tool_call` span). All four ownership-scoped by `(company_id, app_id)`.

`proxy/routes/v1/toolSpans.js` — AI Trace Layer. `POST /v1/tool-spans`, the external-facing counterpart to `mt_ai_record_tool_span()` — a step with no LLM API call at all (or one the caller doesn't want counted as a usage event). Validates `status` against the same enum `usageEvents.js` uses, before calling the RPC — an invalid value reaching the RPC's own `CHECK` constraint would otherwise surface as the RPC's `23514`→`409` mapping, indistinguishable from a genuine idempotency conflict, instead of the `400` a bad-input value should get. No idempotency key on this endpoint — a tool call has no natural client-generated identity to dedupe on.

`proxy/routes/v1/outcomes.js` — v9.32. `POST /v1/outcomes` is a plain `INSERT` — deliberately never `mt_outcome_get_or_create_active`, whose get-or-create behavior is correct for Product Studio's own internal call-grouping but would silently hand back an existing resource on an external REST `POST`, which is not the confirmed contract here. `client_outcome_id` is required (own idempotency key, same role as usage-events' `client_call_id`). `PATCH /v1/outcomes/{id}` completion is ownership-checked and scoped to `status='in_progress'`, returning `404` without distinguishing "doesn't exist" from "belongs to someone else" from "already completed."

`proxy/routes/v1/outcomeTypes.js` — v9.32. `POST`/`GET /v1/outcome-types` — per-app taxonomy registration, scoped by `company_id` as well as `app_id` (a nullable `company_id` column added specifically for this route — `mt_outcome_types` otherwise has no tenant scoping at all, by original design, since Product Studio's own 12-row catalog is global/shared). Re-registration is an idempotent upsert only when `costing_method`/`unit_label` match an existing row (rejected `409` otherwise); `name`/`description`/`canvas`/`abandonment_window_hrs` are always updated on a matching re-registration, not silently left stale.

`proxy/routes/v1/companyApps.js` — v9.32. `GET /v1/company-apps/me` — a credential self-check (`company_id`, `app_id`, `is_active`, `credential_created_at`, never `credential_hash`), via a direct query — deliberately never `mt_company_apps_list`, whose authorization also assumes a human Supabase Auth session.

`proxy/lib/costTower/idempotency.js` — v9.32. Shared `insertIdempotent()` helper used by both `usageEvents.js` and `outcomes.js` — `.upsert(row, {onConflict, ignoreDuplicates:true})` (supabase-js's equivalent of `INSERT ... ON CONFLICT DO NOTHING`), with a follow-up `SELECT` on an empty (conflicted) result rather than treating a dedup replay as an error.

`proxy/lib/costTower/idempotencyStrict.js` — AI Trace Layer. `insertIdempotentStrict()` wraps `insertIdempotent()` (unmodified, still used as-is elsewhere) and adds exactly one thing: on a conflict, re-fetches the existing row's `compareColumns` and rejects with `IDEMPOTENCY_CONFLICT` if any differ from what this call would have inserted — e.g. `POST /v1/traces` replaying `client_trace_id` with a different `agent_name`. Modeled on `outcomeTypes.js`'s existing hand-rolled compare-then-409 pattern rather than a new shape. Compares UUID-shaped values case-insensitively (Postgres canonicalizes `uuid` columns to lowercase on read-back; a caller's fresh request keeps whatever case it sent) — a code-review fix.

`proxy/lib/costTower/usageEventRpcParams.js` — AI Trace Layer, code-review fix. `buildUsageEventRpcParams()` is the single field-name → `p_*` mapping for the `mt_ai_record_usage_event_with_span` RPC, shared by `proxy/server.js`'s `_insertAiUsageEvent()` and `usageEvents.js`'s `_processItem()` — previously duplicated independently in both, which is exactly how this RPC's parameter list drifted out of sync with calling code once already (see the migration file's own Step 4 reconciliation note).

`proxy/lib/costTower/unitsGenerated.js` — v9.32. Scoped update helper (`company_id`+`app_id`+`client_call_id`) backing the units-generated report-back endpoint.

`proxy/openapi/` — v9.32. `openapi.yaml` (the full `/v1` contract, OpenAPI 3.0.3, lints clean via `@redocly/cli`), `docs.html` (standalone Redoc page, no build step), and a locally-vendored `redoc.standalone.js`/`.LICENSE.txt` — not CDN-loaded, since `cdn.jsdelivr.net` is confirmed unreachable from this network (a direct connection failure, not a hypothetical), matching this project's own documented history of corporate-network interference with external requests. Served at `/docs` (see `proxy/server.js`'s bullet above for the redirect reasoning). Contract changelog v1.1.0 (AI Trace Layer) adds the `traces`/`tool-spans` tags, paths, and schemas, plus `client_trace_id`/`agent_name`/`trace_id` on the existing usage-event schemas — fully additive.

`proxy/providerAdapters.js` — canonical, shared adapter module (v9.14, Gemini added v9.14.03). One entry per provider: `buildUpstreamRequest`, `normalizeSuccess`, `normalizeHttpError`, `normalizeTransportError`, plus `MODEL_CATALOG_BY_PROVIDER` for the proxy's own fail-fast model validation. ## capStore data structure

```
capStore[metricKey] = {
  metricName: string,
  stageLabel: string,
  stageId: string,            // 'acquisition' | 'activation' | 'engagement' | 'retention' | 'pi'
  bucketId: string,           // v9.05, 'pi' stageId entries only — identity of the Custom
                               // Process Area/Metric this capability belongs to (see
                               // pi-bucket.js). metricName is display-only for these entries;
                               // bucketId is authoritative for grouping/lookup. Multiple
                               // capStore entries with different names can share one bucketId.
  _piFirst: boolean,          // true for PI-first (path B) entries
  capabilities: [{
    name: string,
    why: string,
    subCaps: [] | null,
    _manual: boolean,         // true if added via Add Capability modal
    featStore: {
      top: [{                 // main feature list
        name, why, selected,
        metric, stage, cap, subCap,
        _aiAdded: boolean,    // true if AI-added to a manual capability
        _piSelected: boolean  // true if checked for PI send
      }],
      sc0..scN: []            // sub-capability feature lists
    }
  }]
}
```

metricKey format: `stageId+'||'+metricName` for KPI-linked entries; `'pi||'+capName` for PI-first entries. **Note (v9.05):** for `pi` stageId entries, the metricKey is derived from the CAPABILITY name (via `ccPIKey()`), not the bucket/process-area name — grouping by process area uses `bucketId`, never the key itself.
