# Changelog — Product Studio

## v9.38 - 2026-09-18: Agent Test Execution Framework: generic evaluator dispatch, judge threshold fix, Discovery Map onboarding

- Fixed - `evaluator.js`'s `script_diff` dispatch was hardcoded to Requirement Agent's own rubric keys and functions (`F`, `A1`, `A2`, `P1`), contrary to its own header comment describing it as generic — found while compiling Discovery Map's test suite, whose 11 `script_diff` rubrics had no matching handler and would have silently done nothing at run time. `evaluate()` now takes an injected `scriptChecks` map and dispatches by looking up `testCase.rubric` in it; each agent supplies its own `scriptChecks.js` (`requirement-agent/scriptChecks.js` holds RA's four original functions moved verbatim, zero behavior change; `discovery-map/scriptChecks.js` implements all 11).
- Fixed - `evalLlmJudge()` computed the real pass/fail threshold (including any per-test-case zero-tolerance override) only *after* the judge had already answered, so the judge was never told the real bar — a case like DM-H05 (rubric threshold 0.9, `judgeContext.strictness: 'zero-tolerance'` pushing the real bar to 1.0) could score 0.95, reasonably report no failure, and then be silently reclassified as a fail with no recommendation attached. The threshold is now computed before the prompt is built and told to the judge (including the zero-tolerance note), plus a backstop synthesizes a recommendation for any fail that still comes back without one.
- Added - Discovery Map onboarded as the second agent in the Agent Test Execution Framework (`test-suite/agents/discovery-map/`): 20 test cases across 7 categories, `invoke-config.js` loading the real, unmodified `scripts/prompts.js` in a Node `vm` context to call its prompt-building functions verbatim rather than a hand-copied approximation; both Gate 1 (product) and Gate 2 (technical fidelity) reviews passed and recorded in `REVIEW.md`.
- Added - The `generate-agent-test-suite` generator is now a one-input skill — agent-name derivation, output-folder resolution, confidence labeling, and the automated smoke-test pre-check all happen inside the generator itself instead of being spelled out per invocation — and now auto-copies `REVIEW-CHECKLIST.md` into each new agent's own `REVIEW.md`, closing a step that was previously manual and easy to forget.

## v9.37.01 - 2026-09-14: Fix column-ambiguity/type-mismatch/period-scoping bugs in the v9.37 aggregation RPCs

- Fixed - Live-app testing and code review surfaced three bug classes across the new v9.37 RPCs, all corrected in `sql/ai-cost-tower-period-aggregation-ambiguous-column-fix.sql` (NOT run by Claude Code): (1) several `RETURNS TABLE(...)` functions named an output column the same as a real source-table column referenced unqualified in the body (e.g. `cache_read_tokens`, `input_tokens`, `request_started_at`, `feature`) — Postgres's default `plpgsql.variable_conflict='error'` then rejected every such reference as ambiguous at call time; fixed with `#variable_conflict use_column` (also applied to `mt_ai_trace_detail_list`, a pre-existing, unrelated function with the identical `trace_id` collision that had apparently never been live-tested before this pass); (2) `mt_ai_cost_grouped`'s `units_generated_sum` column (declared `numeric`) received a `bigint` from `SUM(units_generated)` — `RETURN QUERY` requires an exact type match, unlike a normal assignment — fixed with an explicit `::numeric` cast, plus defensive casts added to every other aggregate output in `mt_ai_cost_grouped`/`mt_ai_cost_opportunities`; (3) `mt_ai_cost_top_calls`'s `outcome_type` partition had no period bound on the joined outcome's `started_at`, unlike its sibling `mt_ai_cost_grouped('outcome_type')` — a call tied to an outcome that started in an earlier period could surface as an Outcome-Based Cost "sample call" for a type whose displayed Total/Completed/Sunk figures correctly excluded it.

## v9.37 - 2026-09-14: AI Cost Control Tower: server-side period aggregation (fixes silent row-cap truncation)

Type 1's candidate-cheaper-tier rate now reads `mt_model_pricing`'s current catalog rate directly rather than averaging other same-period rows happening to be priced at that tier (approved change — more robust, but can shift the displayed savings number vs. a prior period's screenshot).
- Added - Request Explorer's flat table now pages through `mt_ai_cost_events_list` explicitly (1,000 rows/page, `ORDER BY request_started_at DESC`, accurate total count via a window column, Newer/Older page controls) instead of an unbounded fetch that silently stopped wherever the row cap landed; `mt_outcomes_list` gains the same explicit `ORDER BY` as a low-risk hardening (current volume doesn't trip any cap, but truncation would now be deterministic if it ever does).

## v9.34 - 2026-09-12: Universal Payload Capture

- Added - Extends payload capture (v9.33.01/.02) to every Product Studio AI call, not just Requirement Agent's — classified as minor/feature, not a patch, since it changes backend persistence behavior across every AI-calling feature and modifies the shape of an existing, actively-used RPC. `mt_ai_record_usage_event_with_span()` (`sql/ai-cost-tower-trace-layer-payload-rpc-extension-migration.sql`, NOT run by Claude Code — DROP + CREATE FUNCTION, since a plain `CREATE OR REPLACE` cannot add parameters without leaving the old signature callable as a separate overload, the same reason `ai-cost-tower-trace-layer-step4-reconciliation.sql` needed one) gains `p_request_payload`/`p_response_payload` (both `JSONB DEFAULT NULL`) and conditionally writes to `mt_ai_trace_payloads`, gated independently of the trace/span condition on the same `scope_payloads_write`/`payload_capture_enabled` columns the external `/v1/trace-payloads` route already gates on. Adds `payload_capture_status` (`captured`/`gate_disabled`/`not_requested`) to the `RETURNS TABLE` so a denial is observable without changing the usage-event write's own success/failure contract; on a `client_call_id` replay this reflects whether a payload already exists for the original call via a lookup against `mt_ai_trace_payloads`, not a re-derivation. `proxy/lib/costTower/usageEventRpcParams.js` gains the corresponding `p_request_payload`/`p_response_payload` mapping — without it, the RPC's new parameters would never actually be reached from either caller (`server.js`'s `_insertAiUsageEvent()` or `usageEvents.js`'s `_processItem()`), since this helper does an explicit named-field mapping rather than passing fields through; `usageEvents.js` itself needs no change, since it never sets either field and the RPC defaults both to `NULL`. `proxy/server.js`: all four `_insertAiUsageEvent()` call sites (non-streaming success/error-payload, streaming success/mid-stream-error, streaming pre-stream buffered error, and the outer network/timeout catch-all) now offer `request_payload` unconditionally, on the reasoning that the request is fully constructed before any of these outcomes is known; `response_payload` follows one canonical `{schema, streamed, content_type, error, content}` envelope across both transports. Streamed response text is accumulated inside `_streamUpstreamOnce()` at the parsed-SSE-delta level (`parsedEvt.delta`, already a complete JS string), never off a raw network `chunk` — this function's own `StringDecoder` exists specifically because a raw chunk is not guaranteed to end on a UTF-8 character boundary — and stops at the last delta that fits under `MAX_PAYLOAD_CAPTURE_BYTES` (100KB, retunable) rather than ever slicing a completed buffer/string, so a capped capture can never contain a partial character. A genuine mid-stream abort keeps whatever partial text was accumulated (`truncated: false`, kept distinct from actually hitting the byte cap). `_insertAiUsageEvent()` now reads the RPC's returned `payload_capture_status` and logs a `warn`-level line (company_id/app_id/usage_event_id/status, never payload content) on `gate_disabled`. Also fixes a pre-existing, independent bug found while wiring the outer catch-all call site: `body` was a `const` declared inside the route's `try` block, so the catch block's own existing `body.model` reference threw `ReferenceError` on every network-failure/timeout call reaching it, rather than reading as unset — hoisted to a `let` before the `try`, the same fix already applied to `_clientCallId` and others in an earlier build.

## v9.31 - 2026-09-04: Session local-cache restructuring — meta/snapshot split, snapshot-size cap, resync-on-miss

Root cause: `pgt_session_*` entries in `localStorage` (one per session, `scripts/session-store.js`) accumulated indefinitely with no cap — 89 real, legitimately-created, never-deleted sessions in one company/profile hit that origin's storage quota (~5.5MB), causing Supabase's session-init write to fail silently on login and bounce the user straight back to the login screen with no visible error. Shipped as a feature-level version (not a `.NN` patch) because it restructures the local cache's shape across ten call sites in two files, not a scoped bug fix in one function.

- Added - Session cache now splits lightweight metadata (name, savedAt, counts, etc.) from each session's bulky content payload into its own always-complete index. Home's session list reads only that lightweight index now, so every session stays visible there regardless of whether its heavier content is currently cached locally — including one just shared, renamed, or re-shared by a teammate, which previously stayed invisible or stale on Home until an unrelated full sync happened to run.
- Added - Local session content is capped at a 4MB total budget; once an account exceeds it, the least-recently-touched sessions' content is actively evicted, oldest first, so an already-oversized account shrinks on its very next login instead of merely having further growth capped. The currently open session, and any session with an edit not yet confirmed saved to the database, are never evicted. A session deleted on another device, or a company with more sessions than a single fetch can return, is now handled correctly rather than either lingering forever locally or dropping real sessions from view.
- Added - Opening a session whose local content was evicted (or otherwise missing) now quietly re-fetches it from the database instead of failing with "Data may be corrupted" — that message is now reserved for a session that's genuinely gone; a distinct message appears only if the live re-fetch itself fails.
- Fixed - Renaming a session, or toggling it between Shared and Private, silently did nothing at all — not just locally, but never even reaching the server — whenever that session's local content cache was missing or corrupted. Both actions now work correctly regardless of local cache state, with the two now behaving consistently with each other.

## v9.12 — Session Occupancy Lock ("Single User Editing" mode)

**Added — a new Collaborative Editing setting (Settings → Output Depth → Session Sharing)**, replacing the old two-way "View only / Collaborative editing" radio choice with a single on/off toggle plus, once on, a choice between **Single User Editing** (new, default) and **Multi User Editing** (today's existing unrestricted concurrent-edit behavior, fully unchanged, same amber coordination warning as before).

## v9.08 — Read-only shareable sessions

**Added — Session sharing now has two modes: View only (new default) and Collaborative editing:** Previously, sharing a session always granted collaborators full read/write access, identical to the owner's own permissions. A new company-level setting (Settings → Output Depth → Session Sharing) controls the default for newly-shared sessions, defaulting to View only. This is intended to reduce accidental concurrent-write conflicts, which the app's existing full-snapshot save model (no version checking) is vulnerable to.

**Enforcement is server-side, not cosmetic:** The two RPCs that allow a non-owner to write to a shared session (`save_shared_session_content` for content saves, `acquire_generation_lock` for AI generation) now check the session's `share_mode` directly in their authorization logic — a view-only collaborator's client cannot bypass this by calling the RPC directly, since the database itself rejects the write. Client-side UI hiding (the ~29 gated entry points across all screens) is a UX layer on top of this, not the actual security boundary.

**Freeze-on-open for viewers:** A view-only collaborator's client never starts the live-sync watch/poll cycle for that session — they see the snapshot as of when they opened it, with the next fresh fetch happening on their next resume. The owner can continue editing in the background; the viewer simply doesn't see live updates mid-session, consistent with the existing resume-refetch behavior already used for shared sessions.

**Adversarial review process:** This feature went through two rounds of external adversarial review before being built. Round 1 found and closed: a revocation race in the original two-statement RPC authorization pattern (fixed by collapsing into a single conditional `UPDATE ... RETURNING`), a completely separate, previously unaudited write path (`acquire_generation_lock`, which had no `share_mode` awareness at all), and a fail-open client-side default (`_activeSessionShareMode` now defaults to `'view'`, not `'edit'`). **Known non-issues, checked and confirmed clean:** All 5 export functions (PI, Market Intelligence, Diagnostic, XLSX, general DOCX) were checked line-by-line for hidden state-mutation side effects — none found, all remain fully available to view-only users. ## v8.151 — Repeating post-resume toast fix (sc/pc cursor-seeding omission)

## v8.150 — Corrected resume-staleness fix and card-ordering fix, after both were found incomplete in live testing

**Resume-staleness fix, corrected (Issue 2):** the v8.149 attempt was live-tested and found not to actually fix the reported bug. Root cause of the miss: it only protected one specific call site (re-resuming the exact same session), computed via an explicit flag passed in by that one caller — but the actual destructive save happens earlier, the moment someone navigates away to Home at all (a different call site entirely), before they ever get to re-resuming anything. By the time re-resuming happened, the damage was already done and the v8.149 check was already false. Corrected by moving the detection inside the cleanup function itself, automatically, so every caller is protected uniformly — not just one that remembers to opt in. The check itself was also hardened after a flaw found before this shipped: the first design would have kept using the visible notification banner's own state as the signal, which is cleared both by a genuine apply *and* by the user simply dismissing the banner — meaning a dismissal alone would have looked like "nothing pending," silently reintroducing the bug. Uses a new, dedicated flag instead, set when the background watch discovers unapplied changes and cleared only on a genuinely successful apply, plus a check of this browser's own unflushed local edits. A related console error (`generation_lock_not_acquired`) surfacing after the same stale overwrite is consistent with this same root cause corrupting lock-related bookkeeping stored on the same record, not a separate bug.

**Card-ordering fix (Issue 3):** the "Last Active" badge and the actual first-position card in the session grid were being decided completely independently — a fix corrected which session gets the badge, but never touched the grid's own ordering (a separate sort, defaulting to "Last Modified"), so the two could point at different sessions. Now pins the badged session to the front, but only under that default sort — an explicitly chosen alternate sort (alphabetical, by name) is left completely alone, and a badged session already excluded by the current filter/search is never resurrected.

**Known, accepted residual gap in the resume-staleness fix, not further pursued:** the background watch that detects remote changes polls roughly every 10 seconds. In that narrow window between a collaborator's change landing and this browser's own next poll, the new safety check would still say "nothing pending" even though newer content already exists. Closing this fully would require making the cleanup function asynchronous, a larger structural change to a function this project treats as unusually sensitive — not taken on for a residual window this narrow, for an internal tool with a small number of concurrent users.

## v8.149 — D8 copy fix, resume staleness fix, "Last Active" now per-user

**D8 copy fix:** the Story Canvas coarse-apply description always said "updated" regardless of whether the feature was genuinely new — confirmed via live testing this was misleading for a first-time addition (e.g. sending a Diagnostics experiment to Feature Canvas). Now distinguishes "added" from "updated" based on whether the feature existed locally before the apply.

**Resuming a session can no longer entrench staleness (Issue 1):** confirmed root cause — resuming a session already correctly fetches fresh content from the database for shared sessions, but first calls the existing "leaving my session" cleanup, which unconditionally saves whatever's currently in the browser's memory back to the database. Re-resuming the *same* session you're already stale on meant that save wrote your own stale copy over a collaborator's fresher one, moments before the fresh-fetch step that was supposed to fix exactly that. Fixed narrowly: resuming the same, already-active, shared session now skips that pre-emptive save and trusts the incoming fetch completely. Every other use of the cleanup function (switching to a genuinely different session, private sessions, logout) is unaffected — confirmed via a full sweep of every call site. This required a small, explicitly sign-off-approved edit to a function this project's own rules mark as requiring separate approval before any change.

**"Last Active" is now a real per-user, per-account property (Issue 2):** previously computed by sorting every cached session by a single, global "last saved" timestamp that any collaborator's edit could bump — meaning someone else editing a shared session could silently make it show up as *your* "Last Active" session, even if you'd never opened it. Fixed with a new, durable per-person pointer (new columns on `mt_users_companies`, written via a dedicated security-definer RPC — that table has no direct UPDATE policy at all, confirmed before designing this), updated only when a person actually creates or resumes a session, and following them to any device. Everything else that already correctly used the shared global timestamp (the "Updated X ago" line, the explicit "sort by last modified" option) is untouched.
